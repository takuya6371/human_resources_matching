# 報酬の支払いと本人確認 — 懸念点の洗い出し

チャレンジ機能（`docs/challenge-design.md`）で、帰国後の海外在住者に報酬を
払うことを前提にしたときに出てくる論点を、重い順に並べる。

**私は法務・税務の専門家ではない。以下は「調べるべき論点」であって結論ではない。**
ただし Stripe の可否だけは公式ドキュメントで確認した事実として扱ってよい。

---

## 1. Stripe は日本法人では使えない（確認済み）

**これは調査の結果ではっきりしたので、最初に書く。**

Stripe の公式ドキュメントに、プラットフォームの所在国の制限が明記されている。

| 仕組み | 利用できるプラットフォームの所在国 |
|---|---|
| [Connect 越境入金](https://docs.stripe.com/connect/cross-border-payouts) | US / UK / EEA / CA / CH |
| [Global Payouts](https://docs.stripe.com/global-payouts) | **US / GB のみ**（プライベートプレビューも EU と豪州のみ） |

> Stripe は、記載されている地域以外の国へのセルフサービスによる越境入金を
> サポートしていません。
> （Connect 越境入金のドキュメントより）

**株式会社NeBonga は日本法人なので、どちらも対象外。** 営業に相談する以外の道は
ドキュメント上に存在しない。

さらに Global Payouts は Treasury（米国）が前提で、しかも
「**自社で資金移動業登録（MTL）をすでに保有しているビジネス向け**」と
明記されている。つまり規制を肩代わりしてくれる仕組みではない。

### 受取国の問題は、その手前で止まっている

仮にプラットフォーム所在地の問題が無かったとしても、受取側の対応国が怪しい。
Stripe が連結アカウントを作れる国は46か国程度で、アフリカはごく一部。
エチオピアは対象外。セネガル・ケニアは情報が錯綜していて、確認が要る。

**つまり Stripe は、この用途では二重に塞がっている。**

### 代わりに検討するもの

| | 状況 |
|---|---|
| **当事者間（企業が直接送る）** | 規制から離れていられる。**当面はこれ** |
| **Wise** | 日本法人（ワイズ・ペイメンツ・ジャパン）が資金移動業者として登録済み。ケニアは受取対応。**国ごとに個別確認が要る**（セネガルのXOFなど未確認） |
| Payoneer / Thunes / Flutterwave | 未調査。アフリカのカバレッジは Stripe より広い可能性 |
| Stripe 営業に相談 | 塞がっているので、聞くだけ聞く価値はある |

## 2. 支払いを握ると、規制が一気に増える

当事者間なら発生しないが、プラットフォームが資金を預かると出てくるもの。
**Stripe が使えない以上いったん棚上げだが、将来のために書いておく。**

### 資金移動業 / 収納代行

他人のために資金を移動させる行為は「為替取引」にあたり、原則として
**資金移動業の登録**が必要（資金決済法）。登録は小さなスタートアップには重い。

「収納代行」として整理する逃げ道はあるが、2021年の法改正で、支払人が個人の
収納代行には規制が及ぶようになった。ここは支払人が法人・受取人が個人なので
向きが違うものの、**専門家の確認なしに「大丈夫」と判断してはいけない**領域。

**資金に一切触れない構造にすれば、この話は丸ごと消える。** 技術的には、
Stripe Connect の「デスティネーション支払い」のように、プラットフォームが
残高を持たず決済事業者が直接受取人へ払う形。日本法人では Stripe で組めない。

### 犯罪収益移転防止法

資金移動業者になると、取引時確認（本人確認）が法律上の義務になる。
Didit を入れているので土台はあるが、**制裁リスト・PEPのスクリーニング**まで
求められる。Didit がどこまでやるかの確認が要る。

### 外為法

一定額を超える対外支払いには報告義務がある（支払等報告書は3,000万円超など、
区分ごとに基準が異なる）。当事者間なら企業側の義務。

## 3. 税務

### 源泉徴収（企業がいちばん気にする）

日本企業が非居住者に報酬を払うとき、それが**国内源泉所得**にあたるなら
源泉徴収（原則20.42%）が必要になる。

- **人的役務の提供が国外で行われる**場合は、原則として国内源泉所得に
  あたらない → 源泉徴収不要、という整理が一般的
- ただし**著作権の譲渡や使用許諾の対価**と評価されると「使用料」として
  国内源泉所得になり、源泉徴収の対象になり得る
- ソフトウェアやデザインの成果物は、ここの線引きが微妙。
  **契約書の書き方で変わる**ので、ひな形を用意する価値がある
- 租税条約があれば軽減・免除。手続（租税条約に関する届出書）が要る

**これは企業側の実務だが、知らないと企業が止まる。** 想定問答に入れる。

### 消費税

国外で行われる役務の提供は**国外取引**で、消費税の課税対象外（不課税）
というのが基本。ただし「電気通信利用役務の提供」に該当するとリバースチャージの
話が出てくる。受託開発がこれに当たるかは要確認。

### インボイス

海外の個人は適格請求書発行事業者になれない。ただし上の通り不課税であれば
仕入税額控除の問題自体が生じない。**経理が混乱するポイントなので、
企業向けに一言書いておく。**

## 4. 送金と為替

| | |
|---|---|
| 対応国 | **国ごとに違う。** 「アフリカ対応」とまとめて言える事業者は無い |
| 着金手段 | 銀行口座が無い人もいる。モバイルマネー（M-Pesa等）が主流の国も |
| 手数料 | 10万円の報酬に対して数千円かかると、受取側の実感が変わる |
| 為替 | 円建てで約束して現地通貨で受け取ると、変動を受取側が被る |
| 名義 | 本人名義の口座が必要。Didit の氏名と一致するか |

**報酬額を決める画面で「受取方法を確認済みか」を企業に聞く**だけでも事故が減る。

## 5. 本人確認（Didit）

### いまの状態

**もう入っている。** 使われていないだけ。

```
20260827000000_identity_verification.sql   verification_status / provider / ref / detail
20260829000000_didit_verification.sql      Didit固有の処理
supabase/functions/start-verification      セッションを開く
supabase/functions/verification-status     状態を返す
supabase/functions/verification-webhook    判定を書く（唯一の書き込み元）
```

判定を書けるのは Webhook だけで、本人は書き換えられない
（`guard_verification_fields` / `guard_private_verification_fields`）。
**ここの設計は既に正しい。**

### 足りないもの — 何もゲートしていない

`verification_status` は `profileMapper` で読んで表示しているだけ。
企業とつながる経路はどれも素通りする。

```
threads       企業⇄人材の会話を始める      確認なし
interests     興味を示す                   確認なし
applications  求人に応募する               確認なし
```

### 必須化の設計

判定用の関数を1本作って、3つのポリシーに足す。

```sql
-- 本人確認が済んだ人材か。RLSのポリシーから呼ぶ。
create or replace function public.is_verified_talent(p_id uuid)
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1 from public.profiles
    where id = p_id and verification_status = 'verified'
  );
$$;
```

```sql
-- 会話は、人材側が本人確認済みでないと始められない。
-- どちらが始めても同じ。企業は「誰と話しているか」が分かっている必要がある。
alter policy "threads: insert" on threads
  with check (
    (auth.uid() = talent_id or auth.uid() = company_id)
    and is_verified_talent(talent_id)
  );
```

`interests` は向きが2つあるので、`from_type` / `to_type` で分ける。
`applications` は `profile_id` を見る。

チャレンジ機能では、**採用確定（報酬が発生する瞬間）**にも同じ条件を置く。

### 必須化するときの運用

**既存の未確認ユーザーが、ある日突然つながれなくなる。** 段取りが要る。

1. ダッシュボードに「本人確認がまだです」の帯を出す（メール確認の帯と同じ形）
2. 2週間ほど猶予を置く
3. そのあとポリシーを有効化

**イベント当日に注意。** その場で登録した人は本人確認が済んでいないので、
企業とすぐにはつながれない。ブースで「登録したらすぐ企業と話せます」とは
言わないこと。**「登録 → 本人確認 → つながる」の3段**だと伝える。

### Didit 側の未確認事項

- **無料枠の上限。** 来場者が一斉に本人確認すると超える可能性
- アフリカ各国の身分証に対応しているか（国によって精度が違う）
- 制裁リスト・PEPスクリーニングの有無
- 保持される個人データの範囲と保存期間（下の個人情報に関わる）

## 6. 個人情報

### 越境移転

課題の本文に企業の顧客情報が混ざると、それを海外在住者に見せることが
**外国にある第三者への提供**に該当し得る（個人情報保護法）。

**これは実装に落とせる。**

- 課題フォームに「個人情報・顧客情報を書かないでください」を明示
- `src/lib/moderation.ts` の `screen()` にメールアドレス・電話番号の検出を足し、
  投稿前に警告を出す（メッセージ用の仕組みをそのまま使える）

### 本人確認データ

Didit に身分証の画像を渡している。**どこに保存され、いつ消えるか**を
プライバシーポリシーに書く必要がある。`src/legal/privacy.ts` は既に
Gemini（parse-cv）について書いてあるので、同じ粒度で Didit も書く。

削除請求が来たときに Didit 側のデータも消せるか、APIの有無を確認すること。

## 7. 権利と紛争

| | |
|---|---|
| 提案の権利 | 採用されなかった提案を企業が使ったら。**規約に明記が要る**（`src/legal/terms.ts` に章を足す） |
| 成果物の権利 | 契約で定める。ただし著作権の譲渡と書くと源泉徴収の論点に触れる（上記3） |
| 準拠法・管轄 | 国境をまたぐ業務委託。`operator.ts` の `court` は東京地裁だが、相手が海外だと実効性は別問題 |
| 報酬が払われない | 当事者間だと把握できない。**人材側に「受け取った」を記録してもらう**程度が限界 |
| 品質の紛争 | プラットフォームは当事者でないので介入しない、と規約で明示 |

---

## 8. 運用

- **最初の1件をどう埋めるか。** 機能ではなく営業の問題
- **企業の与信。** 報酬を払う能力があるか。初期は運営が直接知っている企業に限る
- **無応答の企業。** 設計済み（`abandoned`）だが、実装を後回しにしない
- **提案の質。** 承認制は出題側にしか効かない

---

## 当面の推奨

1. **支払いは当事者間のまま。** Stripe は日本法人では塞がっており、
   回避策（Wise等）も国ごとの確認が要る。**量が出てから考える**
2. **Didit の必須化は先にやる。** もう入っているので、
   ゲートを足すだけ。工数は小さく、効果は大きい
3. **企業向けの想定問答を用意する。** 源泉徴収と送金の2点で企業が止まる。
   先回りして答えておく（`/challenges` に設置済み）
4. **課題フォームの個人情報対策**は、チャレンジ機能を作るときに同時に入れる
